# Visual — Deep Research 05: Adversarial Technical Review of Architecture Hypotheses

## Executive verdict and assumption review

The adversarial review does **not** overturn the broad DR-04 direction, but it does materially narrow it.

The strongest surviving proposition is not “WGC + D3D11 + UIA is the architecture.” It is:

> **A custom capture/render path based initially on Windows Graphics Capture and D3D11 is credible enough to prototype for cross-monitor Detail, provided capture latency, lifecycle recovery, coordinate translation, and Point-of-Interest tracking are treated as unresolved engineering problems rather than solved platform services.**

Several DR-04 assumptions should be downgraded substantially. In particular, **one universal physical-pixel coordinate space is too simplistic; UI Automation cannot safely be treated as a universally reliable caret/focus oracle; UIAccess does not solve privileged accessibility access generally; Desktop Duplication is not a clean universal fallback; exact workspace restoration is inherently best-effort; and Doxa USB-display compatibility is genuinely unknown until tested on each relevant hardware/driver revision.**

### Assumption verdict table

| DR-04 assumption | Verdict | Adversarial conclusion |
|---|---|---|
| **WGC is responsive enough for continuous magnified Detail** | **Requires experiment** | WGC is explicitly intended for interactive capture and exposes GPU-backed D3D11 frames, but Microsoft specifies no end-to-end latency or guarantee that capture cadence equals display refresh. A Windows 11 24H2 regression report in Microsoft's own sample repository described capture arriving at substantially below expected monitor refresh; the discussion tied behavior to capture update throttling. |
| **One source can efficiently feed multiple views** | **Survives with constraints** | Microsoft documents that one `GraphicsCaptureItem` can be associated with multiple capture sessions, establishing functional multiplicity, not cheap fan-out. It does **not** establish that one captured texture can drive two or three independently paced outputs with negligible extra copies, especially across adapters. |
| **WGC will work acceptably on Doxa USB displays** | **Requires experiment** | Silicon Motion publicly confirms a USB Display product family, but the public material located does not provide enough information to establish WGC capture behavior, adapter topology, cross-adapter costs, or Doxa's precise controller/driver revisions. |
| **Desktop Duplication is a practical fallback** | **Weak** as a universal fallback | It is credible on conventional configurations, but `DuplicateOutput` is tied to the adapter owning the output; whole-desktop capture needs separate duplications per output; output images are not automatically synchronized; and duplication is invalidated by several display/session transitions. Those are awkward properties for precisely the mixed-monitor configurations Visual cares about. |
| **D3D11 is sufficient** | **Survives with constraints** | WGC itself exposes D3D11 capture surfaces and Microsoft's current capture guidance is D3D11-based. No identified Visual requirement currently forces D3D12. Moving prematurely through D3D11On12 can itself introduce synchronization complexity. |
| **Physical desktop pixels are a workable canonical coordinate space** | **Likely false** | Windows' DPI model exposes values in different coordinate contexts, and Microsoft explicitly warns that some APIs are DPI-virtualized while others are not. `GetGUIThreadInfo`, for example, reports its caret rectangle in logical coordinates relative to the caret's window. Visual needs explicit typed spaces and transforms, not an integer `POINT` assumed to mean the same thing everywhere. |
| **UIA + Win32 gives sufficiently reliable caret tracking** | **Weak** | UIA TextPattern2 provides `GetCaretRange`, but the existence of an API contract is not equivalent to provider coverage across Office, browsers, Electron, terminals and custom controls. UIA text geometry can also yield no visible bounding rectangles in cases such as off-screen/degenerate ranges, while Win32 caret information has its own coordinate and control limitations. |
| **UIA focus can safely drive automatic following** | **Weak** | UI focus is evidence of interaction state, not a platform promise that the focused element is the place a low-vision user wants centred. The policy converting focus events into viewport movement is therefore a Visual UX algorithm, not an OS capability. It should begin conservative and manually overridable. |
| **UIAccess gives enough elevated-application coverage** | **Likely false** as stated | Microsoft requires signing, a secure installation location and the UIAccess manifest setting; UIAccess alone does not give a non-admin AT access to high-integrity admin applications, and secure/system surfaces remain outside ordinary coverage. |
| **Monitor roles can survive reconnects** | **Survives with constraints** | Semantic roles are feasible as Visual state, but automatic physical-monitor rematching across identical devices, hubs, port changes and USB graphics cannot yet be considered deterministic. The safer model is heuristic matching plus explicit user confirmation when identity confidence falls. |
| **Same-monitor Inspect can share the custom capture architecture** | **Requires experiment** | It can potentially share capture/render components, but introduces self-capture, exclusion, overlay/input and focus problems that do not exist when Detail is rendered to another monitor. Windows offers capture exclusion for a process's window, while the Magnification API offers a materially different route for in-place magnification. |
| **Capture sessions recover from sleep/hot-plug without user restart** | **Requires experiment** | Microsoft's WGC guidance explicitly requires frame-pool recreation when size/device state changes and discards outstanding frames during recreation. Desktop Duplication explicitly reports `DXGI_ERROR_ACCESS_LOST` on several desktop/mode transitions and requires duplication recreation. Neither contract amounts to “recovery is automatic.” |
| **Workspace restoration is reliable enough to be commercially useful** | **Weak** if marketed as exact restoration; **survives** as best effort | PowerToys' own documentation says apps must first launch and then visibly be moved, admin apps currently have a positioning limitation, single-instance applications behave differently, and application-specific command-line behavior may be needed. |
| **A 60-Hz-oriented architecture is adequate** | **Survives with constraints** | There is no evidence Visual presently needs 144-Hz output, but architecture must not equate “capture event rate” with source refresh or hard-code a 60-Hz pipeline. |
| **Stable Context + Detail provides enough benefit to justify the engineering** | **Requires experiment** | This review found no primary evidence strong enough to establish the specific commercial hypothesis that a second stable compact display materially reduces low-vision navigation burden. The concept remains plausible, but its value must be demonstrated behaviorally before engineering complexity is justified. |

**Architecture-decision readiness: `Ready for technical spikes`.**

It is **not** ready for provisional production-architecture selection. Enough assumptions have survived to justify coding small experiments, but some of the highest-risk uncertainties—interactive capture latency, mixed-DPI POI alignment, semantic caret coverage, cross-adapter behavior and USB-display compatibility—cannot be settled from documentation.

### Strongest falsifying evidence

The most architecture-relevant negative evidence is concentrated rather than diffuse:

| Evidence | Why it matters to Visual |
|---|---|
| **Windows 11 24H2 WGC frame-rate regression report — microsoft/Windows.UI.Composition-Win32-Samples #142, opened April 27, 2025; currently closed.** Users of the Microsoft sample architecture reported markedly fewer captured frames than expected after the OS update. | A recording application can tolerate cadence variation much better than a magnifier following typing or scrolling. WGC's theoretical suitability therefore does not prove interactive-magnifier suitability. |
| **Microsoft requires explicit WGC frame-pool recreation on size/device changes and discards existing frames.** | Lifecycle management is part of the architecture, not housekeeping to add later. |
| **Desktop Duplication is adapter-owned and loses duplication access across important desktop/mode transitions.** | It is not the wonderfully boring “lower-level backup plan” that DR-04 may have implied. |
| **High-DPI Win32 values are not consistently expressed in a single coordinate convention.** Microsoft explicitly discusses DPI virtualization and mixed-DPI complications. | The proposed physical-pixel canonical model risks subtle, application-dependent tracking errors—the sort that make magnifiers feel haunted. |
| **UIAccess is substantially narrower than “access elevated applications.”** | A design that assumes UIAccess fixes accessibility visibility across privilege boundaries would fail in real enterprise/admin cases. |
| **PowerToys cannot guarantee exact workspace recreation even with Microsoft's own Windows expertise.** | Visual should not spend heavily trying to promise stronger general-purpose workspace control unless it has a compelling accessibility-specific reason. |
| **A Microsoft WGC sample issue reported a `dwm.exe` failure after roughly three hours of simultaneously capturing multiple windows on Windows 11 build 22000.434; that issue is closed and should not be generalized to current Windows, but it is useful evidence that sustained multi-session capture has historically exposed failure modes invisible in simple demos.** | Soak testing must be in the prototype programme, not postponed to release testing. |
| **Another Microsoft sample issue reported a fail-fast exception after about fifteen seconds of HWND capture in a .NET 6/Avalonia integration.** It is implementation evidence, not proof of a WGC platform defect. | WGC's public sample path does not remove interop/lifetime hazards from production software. |

The adversarial conclusion is not that WGC is bad. It is that **“WGC works” and “WGC produces a magnifier-grade interaction loop under arbitrary Windows display configurations” are materially different claims.**

## Capture, rendering, and the revised technical model

### WGC under attack

WGC still has important advantages. Microsoft positions it for display/window frame acquisition and interactive experiences; frames arrive as D3D11 surfaces with QPC timestamps, capture can run away from the UI thread, cursor inclusion can be controlled, and a selected item can participate in multiple sessions. Those are unusually good ingredients for Visual.

But the contract leaves four gaps that matter much more to magnification than to screenshots or recording.

**Latency is unspecified.** `SystemRelativeTime` lets Visual measure when captured content was produced, but Microsoft's API contract does not guarantee capture-to-presentation latency. Frame-pool depth is application-selectable, which creates a real engineering trade-off between resilience and stale queued content.

**Cadence is not the monitor refresh contract.** A Windows 11 24H2 issue reported lower capture rates than expected after an OS update. That does not establish a permanent WGC defect, but it kills the stronger assumption that Visual can simply equate 60/120/144-Hz source refresh with capture delivery.

**Lifecycle transitions are explicit.** Content size changes can otherwise produce clipping or undefined parts of surfaces; device or buffer changes require `Recreate`, and doing that invalidates outstanding frames.

**Long-running/multi-session reliability deserves skepticism.** Microsoft's sample tracker contains historical reports involving multiple concurrent captures, successive capture creation, integration-specific access errors, DWM failure and capture-session fail-fast behavior. None should be treated as a universal current Windows limitation, but collectively they argue against extrapolating from a ten-minute demonstration.

**Verdict:** WGC remains the strongest **first spike**, but not a validated foundation.

### Desktop Duplication under attack

Desktop Duplication has the appeal of being lower-level and mature, but several documented properties are adverse to Visual.

`IDXGIOutput1::DuplicateOutput` requires the D3D device to be created from the adapter to which that output is connected. Capturing an entire multi-output desktop therefore requires duplication objects for each output, and Microsoft explicitly notes that there is no built-in synchronization between those output images; the application must use timestamps to synchronize them.

Pointer handling is also less trivial than “the cursor is in the frame.” Depending on circumstances, pointer imagery may already be composed or may have to be handled separately, and multi-output capture requires pointer-state reconciliation. Rotation similarly requires the application to interpret rotated content correctly because duplicated surfaces are returned in their underlying unrotated orientation.

Most damaging for a magnifier, `AcquireNextFrame` can return `DXGI_ERROR_ACCESS_LOST` after desktop switches, mode changes and transitions between DWM/full-screen states, after which the duplication interface must be recreated.

That does not make Desktop Duplication unusable. It makes it a **narrower fallback**:

> Excellent candidate for benchmarking on a conventional single-adapter machine; poor choice to assume will rescue every WGC problem on hybrid-GPU, USB-display or heavily dynamic topologies.

### D3D11 under attack

No identified Visual requirement currently falsifies D3D11.

WGC's native frame-pool API is itself D3D11-centric, so using D3D11 avoids an interop layer merely to obtain a newer API. Additional abstraction layers can manufacture problems Visual does not need.

The reasons to reconsider D3D11 later would need to be specific: demonstrably inadequate cross-adapter sharing, an HDR/color-management requirement D3D11 cannot conveniently satisfy, a presentation-latency target it cannot meet, or some future composition requirement that clearly benefits from D3D12. None has been demonstrated yet.

HDR does add pipeline complexity regardless: Microsoft's WGC documentation notes that capturing Windows HD Color content can require floating-point capture surfaces plus HDR-to-SDR processing to avoid incorrect appearance. That argues for explicitly deferring full HDR correctness if early Visual customers do not require it; it does **not** by itself argue for D3D12.

**Verdict:** **D3D11 survives**, with DirectComposition/Windows composition potentially used as presentation helpers later rather than treated as substitutes for the capture/render model.

### Same-monitor Inspect is not just “Detail on destination = source”

Dedicated-detail Inspect is architecturally clean:

`unchanged source → capture → crop → enlarge → other display`

Same-monitor Inspect is different because Visual's enlarged representation is introduced into the very surface being captured. That raises the possibility of recursive capture, plus input pass-through, Z-order, focus and restoration questions.

Windows provides `WDA_EXCLUDEFROMCAPTURE` for excluding an application's own window from capture beginning with Windows 10 version 2004, so feedback is not necessarily fatal. But exclusion creates another dependency to validate across Visual's supported configurations.

There is also a simpler alternative: the Windows Magnification API already supports full-screen transforms and input-coordinate transformation, although transformed input introduces a UIAccess requirement and its customization surface is much less attractive for a long-term bespoke multi-monitor product. Its older image-scaling callback is deprecated and effectively unusable as the foundation for modern custom rendering.

**Adversarial recommendation:** prototype same-monitor Inspect independently. Do **not** force architectural unity merely because “everything should use the same renderer.” Reuse is not a product feature.

### Revised technical model

The DR-04 abstraction:

```text
Source → Point of Interest → Transformation → Destination
```

is useful but too optimistic. It assumes that “Source”, “Point of Interest” and coordinates are stable facts. They are not.

A safer working model is:

```text
                  ┌──────────────────────────┐
                  │ Topology / DPI / privilege│
                  │ lifecycle / device state  │
                  └────────────┬─────────────┘
                               │
Source ─→ Capture ─→ Frame + explicit source coordinate space
                               │
                               ├──────────────┐
                               │              │
Pointer ───────────────────────┤              │
Caret provider(s) ─────────────┤→ POI candidates
UI focus / foreground ─────────┤  + confidence
Manual user target ────────────┘
                                      │
                         Tracking / policy arbiter
                         ├─ highlight only
                         ├─ follow
                         ├─ temporarily suspend
                         └─ explicit/manual wins
                                      │
                               View specification
                         source region / zoom / state
                                      │
                   coordinate transform into destination
                                      │
                            render / compose / present
                                      │
                           lifecycle + recovery loop
```

The important changes are conceptual.

**POI becomes evidence, not truth.** Mouse, caret and focus can disagree; a provider can be missing; manual interaction can override all of them.

**Coordinate spaces are attached to data.** A caret rectangle is not accepted merely because it contains four integers.

**Tracking becomes policy rather than plumbing.** Finding something and moving the viewport to it are separate decisions.

**Recovery becomes part of normal operation.** A topology change is not an exception in a portable multi-display product; it is a first-class state transition.

## Tracking, privilege, and coordinate architecture

### Caret tracking does not survive as a universal semantic dependency

UI Automation's TextPattern2 genuinely exposes `GetCaretRange`; that is useful and should be exploited where the provider implements it well. But there are two separate questions:

1. **Can Visual ask for a caret?**
2. **Can Visual depend on receiving an accurate visible physical rectangle quickly enough in the Windows applications customers use?**

Only the first is established by the API contract.

UIA text range geometry itself has boundary cases: bounding-rectangle methods are concerned with visible text geometry and can return no usable rectangles for ranges that have no visible geometry. That matters because caret ranges are degenerate text ranges by nature.

The legacy fallback is not clean either. Microsoft documents `GetGUIThreadInfo.rcCaret` in the coordinate system of the caret window and explicitly notes that the rectangle can describe more than the exact insertion mark for edit controls.

The robust model is therefore a **fallback hierarchy with confidence**, for example:

```text
explicit/manual target
        ↓
reliable UIA text caret with geometry
        ↓
legacy Win32 caret information where applicable
        ↓
focused-control rectangle
        ↓
pointer/current viewport
        ↓
do not move
```

That last outcome is important. **“I don't know” should produce stable magnification, not a random jump.**

Visual should therefore avoid a requirement that every supported Windows application provide semantic caret data. Compatibility testing should instead establish tiers: full caret tracking, control-level fallback, and manual/pointer-only behavior.

### Focus tracking should be demoted from controller to signal

The adversarial problem with focus following is less API reliability than semantics.

An OS accessibility focus event means roughly “the UI system's current accessible focus changed.” It does not promise “this rectangle is what the user wants centred on the Detail display.” Popups, transient elements, ribbons, menus, browser accessibility trees and programmatic focus changes can all legitimately participate in accessibility focus.

That leads to a safer initial rule:

> **Visibility first; automatic movement second.**

A focus change can trigger a highlight or update Visual's knowledge of the likely target without immediately repositioning the entire Detail viewport. Automatic following should be reserved for conditions that testing shows are reliably intentional—for example explicit keyboard navigation—and should suspend briefly after manual pan/inspection.

This is a product-policy inference rather than a documented Windows limitation. It is precisely why raw UIA focus behavior requires application-level testing rather than merely an API proof.

### UIAccess is not the security escape hatch

Microsoft's own accessibility security documentation is unusually clear.

UIAccess applications require an appropriate manifest, trusted signing and secure installation. A UIAccess process running for a non-administrator does **not** magically gain access to a high-integrity application launched as administrator; administrator context still matters. Secure/system-level interfaces are outside ordinary UIAccess reach. UWP applications cannot simply opt into UIAccess either.

That materially changes the packaging hypothesis.

Requiring UIAccess from day one would add:

- code-signing and trusted-installation obligations;
- enterprise deployment considerations;
- privilege-related support cases;
- exposure to behavior that still does not cover all elevated/secure surfaces.

The technically conservative starting position is therefore **UIAccess optional rather than foundational**, unless application testing shows that a commercially critical set of workflows genuinely fails without it. If later required, isolating privilege-sensitive accessibility work from the main UI/process deserves investigation, but that is an architecture question for a later phase rather than a conclusion here.

### Physical pixels fail as the universal canonical space

This is the clearest architecture correction from DR-04.

Microsoft's high-DPI guidance explains that Windows applications can coexist at different DPI-awareness levels and that APIs without explicit display/DPI context may provide virtualized values. Per-monitor-aware applications receive different behavior from legacy/system-DPI-aware callers, and DPI changes can occur dynamically during docking or monitor movement.

`GetGUIThreadInfo` then supplies a concrete example: `rcCaret` is expressed in logical coordinates associated with the caret window, rather than conveniently normalized to whatever physical virtual-desktop space Visual has chosen.

So this:

```text
struct Rect {
    int left;
    int top;
    int right;
    int bottom;
};
// "all Rects are physical desktop pixels"
```

is architecturally unsafe.

The safer conceptual model is typed spaces:

```text
DesktopPhysicalPx
MonitorPhysicalPx
WindowLogicalPx
WindowClientLogicalPx
UIAProviderSpace
CaptureTexturePx
DestinationClientPx
DestinationPhysicalPx
```

with an explicit transform chain carrying the source window, monitor, DPI-awareness context, rotation and capture dimensions needed for conversion.

Visual can still use signed physical virtual-desktop pixels as a **useful interchange/reference space**, especially for pointer positions and monitor geometry. What fails is using that representation as proof that every incoming accessibility rectangle already means physical pixels.

The error cases that should become mandatory tests are mixed 100/125/150/200% scaling, negative-coordinate monitors, portrait rotation, moving an application between monitors while typing, system-DPI-aware legacy applications, per-monitor-aware applications, dynamically changed DPI, and source/destination displays with different scaling. Microsoft's DPI guidance explicitly treats mixed-DPI and dynamic display scenarios as application responsibilities.

## Monitor roles, workspace restoration, and Doxa risk

### Monitor roles survive; exact monitor identity does not

There is an important distinction between these claims:

> “Visual can remember that a display is **Reference**.”

and

> “Visual can always identify the same physical panel after every reconnect.”

The first is easy conceptually. The second is where the adversarial cases live: identical panels, devices without useful unique serial identity, dock changes, USB hub changes, port changes, mirror modes, virtual displays and hardware revisions.

Nothing found in this review establishes a Windows-level identity primitive with the semantics “this is unquestionably the same physical screen the user called Reference last Tuesday.” Therefore automatic role restoration should be designed as **confidence-based matching**, not a contractual guarantee.

A sensible product behavior is:

```text
High-confidence device/topology match
        → restore automatically

Ambiguous match
        → show proposed roles and ask once

Materially different topology
        → preserve saved role definition
          but do not silently move the user's work
```

This is an inference from the failure modes, not a prescribed Windows implementation.

That actually improves the product concept. The commercial feature is not perfect EDID archaeology; it is **getting the user back to a comprehensible Context / Work / Reference arrangement quickly and safely.**

### Workspace restoration is weaker than DR-04 suggested

PowerToys provides unusually strong adversarial evidence because Microsoft is trying to solve almost exactly the mainstream half of this problem.

As of its documentation updated September 14, 2026, PowerToys Workspaces states that it cannot instruct an application to launch initially at the desired position. It launches the app, then moves/resizes it, causing visible repositioning. Different applications react differently when an instance already exists; some need application-specific CLI arguments; single-instance applications behave differently; and applications launched as administrator have a known positioning problem. Workspaces also cannot reproduce Windows snapping state exactly through the public positioning facilities it uses.

That is quite damning evidence against the strong version:

> “Visual will reliably restore the Windows desktop.”

It does **not** invalidate the useful accessibility version:

> “Visual restores its own zoom/contrast/role state, then assists with or best-effort restores known application placement.”

Those are very different support promises.

The simplification opportunity is substantial: **make Visual-state restoration deterministic; treat third-party application restoration as convenience.** Do not make low-vision users' confidence in their magnifier depend on Outlook deciding to open the same sort of window it opened yesterday.

### Doxa remains a hardware laboratory question

Silicon Motion's current public material confirms that the company continues to offer **USB Display** / display-interface solutions for multi-display and docking applications. What the public material retrieved does **not** establish is the exact Windows graphics topology, capture support, compression behavior, adapter relationship or driver implementation for any specific Doxa hardware revision.

Nor did this review locate authoritative public evidence establishing that all Doxa units use the same Silicon Motion controller or driver stack.

Consequently these statements would all be premature:

- “Doxa panels are ordinary outputs from WGC's perspective.”
- “They appear on the same adapter.”
- “Desktop Duplication supports them.”
- “Rendering onto them is zero-copy.”
- “Two USB outputs behave like one HDMI plus one DisplayPort output.”
- “All Doxa units are 60 Hz.”
- “A driver update cannot alter their topology.”

The correct result here is **unknown — physical test required**.

That uncertainty is also an argument **for keeping core Visual generic**. Nothing discovered justifies tying Visual's fundamental abstraction to a particular USB graphics architecture before ordinary GPU-connected monitors work reliably.

### What must wait for physical Doxa units

At least two representative units from each commercially relevant hardware/controller revision should be tested, rather than treating “Doxa” as one device.

| Physical test | What can fail |
|---|---|
| Enumerate adapters/outputs and Windows display identities before/after repeated unplug/replug | Role mapping, adapter assumptions, persistent identity |
| Run WGC display capture from every panel while rendering Detail to each other panel | Unsupported capture, hidden copying, latency, frame-rate behavior |
| Repeat using Desktop Duplication | `DuplicateOutput` support, adapter/device requirements, driver incompatibility |
| Measure source-change → photon/camera-visible destination response during pointer motion, scrolling and typing | USB transport/capture latency making continuous Detail unpleasant |
| Two- and three-display simultaneous output/capture | USB bandwidth, compression, frame pacing, GPU/CPU cost |
| Sleep/resume, lid close/open, dock disconnect/reconnect, USB hub disconnect, driver restart | stale capture items, lost roles, blank windows, recovery failure |
| Mixed scaling and portrait/landscape | coordinate and capture-region errors |
| Teams/Zoom screen sharing while Visual runs | composition/capture interactions and presentation behavior |
| Cursor capture and pointer movement between native-GPU and USB panels | duplicated/missing pointer, lag, discontinuity |
| Actual refresh-mode enumeration | whether 60-Hz-only assumptions are legitimate |
| Long soak, including video and rapid scrolling | driver/resource leakage and recovery problems |

The same suite should be rerun when Doxa changes controller, firmware or Windows driver package. Certification should be **revision-specific**, not brand-specific.

## Product hypothesis challenge and simplification opportunities

### Stable Context + Detail is still worth testing—but it has lost its presumption of innocence

The strongest adversarial result is not technical. It is evidential.

This review did **not** find primary low-vision evidence sufficiently strong to establish the precise claim:

> “Keeping a separate 14–15 inch context display stable while a second display follows magnified detail measurably reduces navigation effort enough to justify continuous capture, tracking and cross-monitor rendering.”

That matters. There is a danger of the project falling into self-confirmation: the architecture is interesting, therefore the workflow feels distinctive, therefore distinctiveness is taken as evidence of value.

Several plausible failure mechanisms should be treated seriously:

**The overview may simply be too small.** A 14–15 inch “whole desktop” can provide spatial context yet be visually unusable to someone who needs substantial magnification.

**Gaze switching may substitute one navigation burden for another.** Instead of panning a magnified viewport, the user repeatedly moves attention and gaze between physical displays.

**Peripheral field loss can make multiple screens particularly unattractive.** More physical desktop is not automatically more usable visual field.

**Users may ignore Context.** If most task decisions occur in Detail, the context monitor can degenerate into an expensive minimap.

**Speech may solve some context problems more efficiently.** For users already combining speech and magnification, another visual surface may be the wrong answer.

**Mild-vision users may prefer Inspect + Return.** An occasionally enlarged control or paragraph requires far less machinery than permanently maintaining a live second representation.

These are **hypotheses to test**, not established prevalence findings. The absence of strong validating evidence is itself the reason Context + Detail belongs in a behavioral prototype before a large engineering commitment.

The appropriate product verdict remains:

**Stable Context + Detail — worth prototype investment; not yet entitled to dictate the production architecture.**

### High-value simplifications revealed by the attack

The adversarial review produces a noticeably simpler potential Visual.

| Remove/defer | Simpler working hypothesis | Why |
|---|---|---|
| Universal automatic caret following | **Pointer/manual first; caret where high confidence exists** | Avoid making product reliability depend on uneven semantic providers. |
| Raw focus-driven viewport movement | **Focus highlight first; movement only under proven rules** | Reduces involuntary panning and event-noise sensitivity. |
| Mandatory UIAccess | **Run normally initially; introduce elevated helper only if critical workflows demand it** | UIAccess has deployment cost and still does not solve every privilege boundary. |
| Exact workspace restoration | **Restore Visual state exactly; third-party windows best-effort/assisted** | Mirrors limitations Microsoft itself documents in Workspaces. |
| Desktop Duplication as automatic universal fallback | **Benchmark it only for configurations where adapter ownership is straightforward** | Its documented lifecycle and multi-output semantics are substantially more involved. |
| Same-monitor Inspect on the continuous-Detail architecture | **Prototype using the simplest in-place mechanism separately** | It has qualitatively different exclusion/input requirements. |
| D3D12/D3D11On12 pre-emptively | **Stay D3D11 until a measured requirement breaks it** | WGC is natively D3D11-oriented; additional interop can introduce new failure modes. |
| HDR perfection initially | **Define an SDR support envelope unless customer evidence demands more** | HDR capture adds pixel-format and tone-mapping requirements. |
| Three simultaneous live derived views | **Prove one Context + one Detail first** | Triple-output load and value are both currently assumptions. |
| Fully automatic monitor-role matching | **Confidence-based match with user confirmation on ambiguity** | Wrong automatic restoration is worse than a five-second question. |

The most interesting strategic simplification is therefore:

> **Visual may not need “an accessibility engine that always knows where the user is.” It may need a fast visual engine plus several increasingly confident ways of suggesting where Detail should look.**

That is a much less brittle proposition.

## Capture and tracking architecture verdicts

### Capture architecture

| Approach | What survived | What broke under attack | Spike verdict |
|---|---|---|---|
| **Windows Graphics Capture + D3D11** | GPU-backed monitor/window frames; modern Windows API; QPC timestamps; cursor control; D3D11-native path; multiple sessions per selected item. | No magnifier-grade latency guarantee; cadence can vary with Windows versions; explicit resize/device recovery; historical multi-session/integration failures. | **Yes — highest priority.** |
| **DXGI Desktop Duplication + D3D11** | Mature low-level output capture; explicit dirty/move rectangles; useful comparator and potentially useful conventional-monitor backend. | Adapter-local device requirement; one duplication per output for desktop; no automatic output synchronization; pointer/rotation work; access loss during important transitions. | **Yes, but as benchmark/fallback spike—not presumed secondary architecture.** |
| **Windows Magnification API** | Very cheap route to proving same-monitor full-screen magnification/Inspect; native source rectangle and transform model. | Less flexible for Visual's independent multi-monitor derived views; transformed input can require UIAccess; old custom-scaling callback is deprecated. | **Yes for same-monitor Inspect proof; weak as entire Visual foundation.** |
| **WGC + D3D11 + composition/presentation helper** | Preserves WGC flexibility while allowing presentation layer to evolve separately. | Adds complexity if adopted before a measured need. | **Credible later; no need to spike independently yet.** |
| **Window-level rather than full-monitor capture** | Can reduce captured area and isolate a task in certain workflows. WGC directly supports window capture. | Does not naturally represent cross-application desktop navigation, popups or transitions between windows; risks turning Visual into application-specific magnification. | **Useful specialized mode, not core replacement.** |

The right pre-implementation stance is therefore **WGC-first, not WGC-faithful**.

### Tracking architecture

| Signal | Appropriate initial role | Automatic Detail movement? | Main qualification |
|---|---|---|---|
| **Mouse pointer** | Primary geometric POI and locator | **Yes**, when pointer-follow is explicitly enabled | Global position is comparatively concrete; still test monitor crossing and cursor/capture timing. |
| **Explicit user target / Inspect command** | Highest-confidence POI | **Yes** | User intent is direct; technically and cognitively simplest. |
| **Text caret via UIA** | High-value enhancement when geometry is valid | **Conditional** | Provider coverage and geometry must be verified; never assume success solely because TextPattern2 exists. |
| **Win32 caret** | Fallback | **Conditional** | Coordinates and exact caret geometry require contextual conversion; application coverage is limited. |
| **UIA focus** | Visibility cue / POI candidate | **Not by default** | Focus is too semantically broad to equate automatically with desired magnification position. |
| **Foreground/window activation** | Context switch signal | **Usually no direct pan** | Better used to change tracking policy or Visual state than to centre blindly. |
| **UIAccess** | Optional privilege mechanism | N/A | Adds deployment constraints and does not remove all privilege boundaries. |

This points strongly toward the DR-03 UX hypothesis **“visibility first, automatic movement second.”** The adversarial technical evidence makes that approach more attractive, not less.

### Coordinate architecture verdict

**Physical virtual-desktop pixels should be demoted from “canonical truth” to “one important space in a transform graph.”**

A coordinate datum should conceptually carry at least:

```text
value
origin / owner
coordinate-space type
DPI context if relevant
monitor / window association
timestamp
confidence / validity
```

The intended conversion should then be explicit:

```text
Provider/client space
      ↓
screen space appropriate to that process/window DPI context
      ↓
physical source/display pixels
      ↓
capture texture pixels
      ↓
cropped Detail source rectangle
      ↓
destination physical/client pixels
```

This looks more complicated than the DR-04 physical-pixel model because Windows **is** more complicated than the DR-04 model. Hiding that complexity in an untyped `RECT` will not eliminate it; it will merely relocate it into bugs.

## Experimental programme and Doxa certification work

The goal of the next phase should not be to build “Visual Alpha.” Five small spikes can eliminate most of the dangerous uncertainty.

### Interactive capture latency and lifecycle spike

**Hypothesis:** WGC can sustain a Detail view whose visual lag is acceptable during pointer movement, typing, fast scrolling and window dragging, and can recover programmatically from ordinary display lifecycle changes.

**Minimal test:** capture a normal GPU-connected source display with WGC; render a cropped 2×–6× Detail region to another display with the smallest possible D3D11 presentation path. Add no product UI beyond selecting the source, zoom and POI. Record WGC `SystemRelativeTime`, app frame-arrival time and presentation timing.

Test 60 Hz and at least one available >60-Hz configuration rather than treating 60 Hz as the architecture. Repeat fast scroll, browser video, Office editing, dragging, display resolution changes, hot-plug and sleep/resume. OS-build recording is mandatory.

**Measure:** median and tail frame age; dropped/stale frames; capture cadence versus source cadence; visual response to pointer motion; GPU/CPU use; blank-frame duration after lifecycle changes; automatic recovery success.

**Falsification criterion:** WGC consistently produces perceptibly stale Detail under ordinary interaction, develops frame backlog that cannot be eliminated by sensible frame-pool/presentation policy, or cannot recover from common display transitions without restarting the application.

### Coordinate and POI reliability spike

**Hypothesis:** A typed transform layer plus UIA/Win32 fallbacks can locate enough real Point-of-Interest targets accurately for useful optional caret/focus assistance.

**Minimal test:** no magnifier required. Draw diagnostic markers for pointer, UIA caret, Win32 caret and focused-element geometry over a captured screenshot/monitor representation.

Exercise Word, Excel, Outlook, Edge, Chrome, Firefox, Teams or current Electron applications, Windows Terminal, Notepad, WinUI/WPF and at least one legacy Win32 application. Repeat on mixed 100/125/150/200% displays, including a negative-coordinate and rotated display.

**Measure:** availability rate per signal/application; rectangle-to-pixel alignment error; event-to-visible-change latency; stale/invalid observations; how often focus produces an obviously inappropriate proposed target.

**Falsification criterion:** semantic caret geometry is missing or materially misaligned in enough mainstream applications that caret-follow would have to be marketed as universally reliable, or coordinate conversion remains application-specific rather than systematically transformable.

A failure here should simplify Visual, not sink it: pointer/manual targeting remains viable.

### Multi-view and adapter-topology spike

**Hypothesis:** one captured source can economically support two independent Visual outputs without a second capture path or unacceptable GPU-copy/pacing cost.

**Minimal test:** use one WGC capture and render two differently cropped/scaled views, first on the same graphics adapter, then on a PC with two graphics adapters where available. Compare against two WGC sessions using the same `GraphicsCaptureItem`.

**Measure:** GPU copy count where observable; GPU/CPU utilization; memory bandwidth; presentation latency per destination; frame synchronization; effect of independently refreshing two destinations; 2-monitor versus 3-monitor operation.

**Falsification criterion:** a third derived view materially increases latency or resource use for the primary Detail view, or cross-adapter destinations require enough synchronization/copy infrastructure to undermine the supposed simplicity of the design.

This spike should establish whether triple-monitor Visual naturally scales from dual-monitor Visual or should instead treat the third panel as a mostly conventional/reference application display.

### Same-monitor Inspect architecture spike

**Hypothesis:** temporary same-monitor enlargement can be implemented without contaminating source capture, stealing focus or creating perceptible restoration artifacts.

**Minimal test:** implement the same user behavior twice:

**A:** WGC + small custom enlargement overlay excluded from capture where possible.

**B:** Windows Magnification API transform.

No settings system, tracking engine or animation framework is necessary.

**Measure:** activation latency; recursion/artifacts; focus change; pointer/input correspondence; exact restoration; interaction with overlapping windows; behavior over rapid repeated activation.

**Falsification criterion:** the custom capture implementation requires disproportionately more machinery than the Magnification API for no user-visible benefit, or neither approach can produce an immediate, stable return to the previous visual state.

This is deliberately allowed to conclude that same-monitor Inspect should use a different backend from cross-monitor Detail.

### Monitor-role and workspace spike

**Hypothesis:** semantic monitor roles remain useful even when third-party application restoration is deliberately best-effort.

**Minimal test:** persist Visual's own role assignment and visual state across reorder, resolution change, scaling change, cable moves and simulated ambiguous topologies. Add only optional move-to-role commands for a few third-party windows; do not build a generic session manager.

**Measure:** automatic role-match correctness, ambiguity rate, user-confirmation frequency, recovery after topology change, and third-party positioning failure categories.

**Falsification criterion:** physical-display rematching is ambiguous often enough that “persistent monitor roles” become more confusing than explicit selection, or the user value disappears once exact application restoration is removed.

### Separate Doxa experiments

Physical Doxa work should begin **after** the ordinary-PC capture/coordinate prototypes produce measurable baselines. Otherwise, when something is slow, it will be impossible to tell whether Visual, WGC, Windows, the USB graphics driver or USB transport is responsible.

For each materially different Doxa hardware/driver revision, compare against the same native-GPU baseline:

| Doxa experiment | Required result before certification |
|---|---|
| **Enumerate topology and adapters** | Every panel is unambiguously detected; topology after reconnect is understood. |
| **WGC capability matrix** | Capture every Doxa source → render to native display; native source → Doxa destination; Doxa source → another Doxa destination. |
| **Desktop Duplication matrix** | Establish support or explicitly declare it unsupported; do not assume fallback equivalence. |
| **Latency benchmark** | Pointer, typing and scroll response compared directly with HDMI/DP baseline. |
| **Two/three-panel load** | Detail responsiveness remains acceptable while all intended panels operate. |
| **Hot-plug/sleep/dock cycling** | Visual self-recovers or presents a deterministic recovery action; no silent stale mapping. |
| **Mixed DPI/orientation** | POI alignment remains correct. |
| **Long soak** | No progressive stale frames, blank panels, resource growth or driver instability. |
| **Teams/Zoom/share testing** | Visual and conference capture coexist predictably. |
| **Controller/driver revision regression** | Results stored against controller identity, driver version and Windows build rather than “Doxa works.” |

Silicon Motion's public material establishes that USB display technology is an active product category; it does not provide evidence strong enough to pre-certify any of these behaviors.

## Final architecture readiness

### What survives DR-05

The **source → transformed view → destination** idea survives. The important insight from DR-04—that a Visual view need not be permanently synonymous with a particular physical monitor—still looks sound.

**WGC + D3D11 survives as the best first experimental path**, because it offers the right functional shape with fewer documented multi-output constraints than Desktop Duplication and substantially more flexibility than the Magnification API.

**D3D11 survives.** There is no evidence-based reason to introduce D3D12 now.

**Independent destination views survive conceptually**, but efficient fan-out and cross-adapter operation require measurement.

**Monitor roles survive as semantic Visual state**, provided automatic device rematching is fallible and user-correctable.

### What does not survive intact

The assumption that **physical desktop pixels can be the single canonical coordinate representation is likely false**. Windows DPI behavior demands typed spaces and explicit transforms.

The assumption that **UIA + Win32 can provide a universally dependable caret/focus POI is weak**. Those signals should enhance Visual when confidence is high, not be structural requirements for magnification to function.

The assumption that **UIAccess solves elevated-application coverage is false in its strong form**.

The assumption that **Desktop Duplication is a simple universal Plan B is weak**. It is a useful comparator and potentially a backend for constrained configurations, but adapter ownership, output synchronization and lifecycle invalidation are precisely the kinds of complexity Visual hoped a fallback would avoid.

The assumption that **workspace restoration can be exact is weak**. Microsoft's own PowerToys implementation demonstrates why “launch and move things approximately back” is a more honest contract.

The assumption that **same-monitor Inspect is merely another destination configuration is unproven**. It deserves an independent, deliberately cheap implementation experiment.

Most importantly, the assumption that **Stable Context + Detail is commercially worth all this machinery remains unproved**. The engineering should not outrun the product evidence.

### The smallest decision set before implementation

The project does **not** need another broad architecture survey. It needs measured answers to four questions:

> **Can WGC deliver a continuously magnified second-screen view with sufficiently low and stable interactive latency through normal Windows lifecycle changes?**

> **Can Visual map pointer/caret/focus observations accurately into captured pixels across mainstream applications and mixed-DPI displays without making semantic tracking mandatory?**

> **Can one capture economically drive the dual-/triple-monitor views actually needed, including realistic adapter boundaries?**

> **Is same-monitor Inspect better implemented as part of the custom capture pipeline or as a deliberately separate, simpler magnification mechanism?**

Monitor-role restoration is the fifth, lower-risk spike; Doxa compatibility follows as hardware certification rather than as an architectural assumption.

The appropriate DR-05 conclusion is therefore:

> **Ready for technical spikes.**

Not “ready for provisional architecture selection,” because WGC's magnifier-grade latency, multi-view behavior, semantic tracking reliability and USB-display compatibility remain experimentally unresolved.

Not “evidence contradicts the current direction,” because nothing found makes WGC + D3D11 implausible; indeed Microsoft's current capture contract remains broadly compatible with the desired cross-monitor experience.

The architecture coming out of the adversarial review should therefore become **less ambitious before it becomes more sophisticated**:

```text
WGC first, not WGC only.
D3D11 until evidence says otherwise.
Typed coordinates, not magic pixels.
Manual/pointer intent first, semantic tracking second.
Visual-state restoration first, desktop restoration second.
Dual-view proof before triple-view enthusiasm.
Ordinary Windows proof before Doxa certification.
And Context + Detail remains a hypothesis—not a religion.
```

That smaller architecture preserves nearly all of Visual's distinctive product opportunity while removing several assumptions most likely to turn into long-lived compatibility and support liabilities.
