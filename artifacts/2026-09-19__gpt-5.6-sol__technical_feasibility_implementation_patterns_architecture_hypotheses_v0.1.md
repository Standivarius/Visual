# Visual — Deep Research 04: Technical Feasibility, Implementation Patterns, and Architecture Hypotheses

**Research position: 19 September 2026**

The technical picture is encouraging. Visual’s core proposition does **not** appear to require recreating a system-wide ZoomText-class magnification engine before the product concept can be tested. On ordinary Windows 11 hardware, the most important experience — keeping one monitor stable while another shows magnified detail — maps quite naturally to a pipeline of **capture → select region → GPU scale/process → render into an independent window on another display**. Windows Graphics Capture already exposes captured frames as Direct3D surfaces, while DXGI Desktop Duplication provides a lower-level alternative when more control is required.

The harder engineering problems sit around that pixel pipeline: determining **what** should be magnified from mouse/caret/focus signals; reconciling Windows' several coordinate systems under mixed DPI; recovering cleanly when monitor topology changes; remembering the identity and role of physically similar displays; supporting elevated applications; and determining whether USB-display hardware behaves like conventional GPU-attached monitors for capture and rendering. Microsoft's own accessibility, display-management and PowerToys implementations provide useful precedents for most of these problems, but none eliminates the need for focused experimentation.

The strongest **architecture hypothesis to test first** is therefore a **Windows Graphics Capture + D3D11 custom-view architecture**, with UI Automation and Win32 accessibility signals for Point-of-Interest tracking and Windows display APIs for monitor roles. That is a hypothesis, not a recommendation to commit: Desktop Duplication deserves a head-to-head latency/compatibility spike, and the Windows Magnification API remains attractive for very cheap behavioral prototypes.

The most important uncertainty is not whether Windows can enlarge pixels. It plainly can. The uncertainties are whether Visual can do so with **low enough delay, sufficiently reliable semantic tracking, stable enough coordinates, and acceptable behavior across ordinary GPUs and later Doxa USB displays** without accumulating the machinery of a mature full-screen magnifier.

The important architectural separation is therefore:

**Source** → **Point of Interest** → **View transformation** → **Destination**

rather than:

**Monitor** → **magnification setting**.

That distinction matters. A source monitor should potentially feed two views; a destination should be able to show a region originating on another monitor; and a user's pointer, caret or focus can identify the Point of Interest without dictating the output monitor. WGC delivers captured frames as D3D resources, making this source/view separation technically plausible; the fan-out efficiency still needs measurement.

### Stable Context + Detail

Three technically credible implementations emerge.

**WGC custom-view hypothesis.** Create a `GraphicsCaptureItem` for the source monitor, receive frames via `Direct3D11CaptureFramePool`, map the current Point of Interest into source-pixel coordinates, crop the corresponding rectangle, and render that rectangle with D3D11 into a borderless window located on the Detail monitor. Windows Graphics Capture supports monitor and window capture, uses a D3D device/frame pool, and supports programmatic monitor targeting through `IGraphicsCaptureItemInterop::CreateForMonitor`.

This is conceptually the cleanest implementation because **the Context monitor need not be transformed at all**. Visual merely observes it. Detail is an independently rendered second view. Context stability is therefore a product policy rather than an intricate full-desktop transformation.

**DXGI Desktop Duplication hypothesis.** Duplicate the source output, obtain each acquired frame as an `ID3D11Texture2D`, select the desired rectangle, then render it into the Detail window. Desktop Duplication provides dirty/move metadata and pointer information and is explicitly designed for GPU processing of desktop frames. It is lower-level: rotation and some pointer composition are the application's responsibility, and a duplication interface is associated with an adapter output.

**Magnification API hypothesis.** Use a windowed magnifier control placed on the second display and repeatedly update its source rectangle according to the selected POI. The Magnification API exposes source-rectangle and transform operations and was expressly designed for assistive magnification, so this is a reasonable fast prototype. Its older model and constraints make it less obviously suited to a flexible many-source/many-view architecture.

No public evidence requires Visual to capture or rewrite the entire Windows desktop simply to provide Context + Detail.

### Pointer, caret and focus are three different data sources

Visual should technically preserve the distinction discovered in the UX research.

A pointer position is effectively a continuously changing spatial signal. A caret is a semantic text-editing signal. Keyboard focus is an object/control signal. Microsoft's own Windows Magnifier treats pointer, keyboard focus, text cursor and Narrator cursor as separately configurable follow targets, which reinforces the wisdom of keeping them separate inside Visual rather than collapsing them into a single generic “tracking” mechanism.

For **text caret**, `IUIAutomationTextPattern2::GetCaretRange` can return the caret-associated zero-length text range and whether its text control has keyboard focus; the resulting range can be used to obtain caret-region information. This is much stronger semantically than trying to infer typing position from the mouse.

It is not enough on its own. `GetGUIThreadInfo` exposes GUI-thread information including a caret rectangle, but Microsoft documents quirks around caret/window state; `GetCaretPos` returns client-relative caret coordinates and has its own coordinate semantics. These make them useful fallbacks, not interchangeable replacements for UI Automation.

For **keyboard focus**, UI Automation exposes global focus-changed events. Microsoft's event guidance warns that some UIA events can arrive even when the corresponding state has not meaningfully changed, so Visual should expect to verify/debounce rather than moving the viewport on every raw accessibility event.

WinEvent hooks provide another global observation path. Out-of-context hooks are asynchronous and queued, require an event/message-loop model, and Microsoft warns about reentrancy/event-order behavior. That suggests a **signal-fusion** approach rather than treating a single event stream as unquestionable truth.

A provisional fallback hierarchy is therefore:

**UIA semantic signal → Win32 accessibility/GUI signal → current foreground/focus context → no automatic movement**

rather than attempting ever more heroic guesses. That final “do nothing” is important: an incorrect automatic pan is often worse than leaving the view still.

### Why D3D11 remains the sensible baseline

There is no evidence here that Visual needs D3D12. WGC is already built around Direct3D capture surfaces, Desktop Duplication directly returns D3D11-compatible textures, and D3D11 provides the resource/context model needed to crop, scale, apply relatively simple pixel effects and present into independent windows.

**Architecture inference:** start from D3D11 unless measurement exposes a specific bottleneck that D3D11 cannot resolve. Moving to D3D12 merely because the product is graphics-heavy would be technology theatre rather than evidence-led engineering.

For an early prototype, even D3D11 need not be architecturally elaborate. One capture source, one retained latest-frame texture, one crop transform and one borderless output window are sufficient to test the principal Context + Detail interaction. The production questions — multiple devices, cross-adapter resources, effects, frame pacing, recovery and HDR — can remain outside the first behavioral prototype.

### The coordinate problem is more dangerous than it looks

The product will encounter at least these coordinate spaces:

- Windows virtual-desktop coordinates;
- monitor-relative coordinates;
- physical capture pixels;
- DPI-scaled/logical application coordinates;
- UIA-derived element/caret rectangles;
- Win32 client coordinates;
- capture-texture coordinates;
- Detail-output pixels;
- potentially rotated source coordinates.

Microsoft's DPI guidance explicitly warns that mixed scaling, docking and Remote Desktop can alter DPI topology and that not every Win32 API uses identical DPI semantics. Microsoft's `GetCaretPos` and `GetGUIThreadInfo` documentation further illustrates that caret coordinates may be client-relative/logical rather than immediately usable as capture-texture pixels.

Desktop Duplication adds another trap: with a rotated display, the acquired surface dimensions remain in an unrotated orientation while the desktop image inside it is rotated; the client must transform the content appropriately.

**Recommended coordinate hypothesis:** use **signed physical virtual-desktop pixels** as Visual's canonical spatial domain wherever a signal can be normalized into it. Every monitor should then carry explicit metadata:

`desktop physical rect + DPI + scaling + rotation + capture dimensions + output role`.

Each input provider converts into canonical coordinates once; each capture backend converts canonical coordinates into texture coordinates once; each output renderer converts its selected source rectangle into destination pixels. This should be treated as an experimentally validated abstraction rather than assumed correctness, because UI Automation and older Win32 APIs may require provider-specific conversions.

The eventual coordinate test matrix needs, at minimum, monitors positioned left and above the primary display so coordinates become negative; 100/125/150/200% scale combinations; different resolutions; 90°/270° portrait rotation; primary-monitor changes; docking/reconnection; identical display models; sleep/resume; and a source monitor whose DPI differs from the Detail monitor. Those are test requirements inferred directly from Windows' mixed-DPI, topology and rotation behavior.

PowerToys is especially relevant to **Monitor Roles**. The source currently records `monitor-instance-id`, `monitor-serial-number`, `monitor-number`, DPI, virtual desktop ID, work-area position and dimensions rather than trusting a single unstable identifier.

### Public commercial-product signal

Public documentation from closed-source magnifiers tells us what behavior exists, but not how it is implemented. That boundary matters.

Windows Magnifier separately supports following the mouse pointer, keyboard focus, text cursor and Narrator cursor; it also provides quick return/toggle behavior around 1× and a temporary whole-screen overview while zoomed. These are useful interaction precedents for Visual's tracking and Inspect + Return concepts, but they reveal nothing about Microsoft's internal rendering architecture.

Current Freedom Scientific documentation confirms ZoomText's familiar keyboard-centric magnification model and broad zoom range, but there is no defensible basis here for reverse-engineering its capture or graphics architecture from those behaviors.

Low Vision Zoom's current Microsoft Store presentation emphasizes lightweight, smooth enlargement rather than abrupt magnification changes. That is useful UX signal but gives no public implementation detail.

No architecture conclusion in this report depends on hypothesized internals of ZoomText, SuperNova or Low Vision Zoom.

## Feature implementation hypotheses

### Stable Context + Detail

**Approach A — WGC source, custom D3D11 Detail output**

```text
Source monitor
   ↓
GraphicsCaptureItem / frame pool
   ↓
latest D3D11 frame
   ↓
POI → source crop rectangle
   ↓
D3D11 scale / optional effects
   ↓
borderless Detail window on destination monitor
```

WGC already hands the application a Direct3D surface, so the crop does not need to round-trip through system memory in the normal case. The frame pool can be recreated when capture dimensions change, which is relevant to display mode/topology changes.

**Likely complexity:** Medium.  
**Main unknowns:** measured latency, multiple-source/multiple-view load, same-monitor capture feedback, cross-adapter behavior, USB displays.

**Approach B — Desktop Duplication source, custom D3D11 Detail output**

```text
DXGI output
   ↓
IDXGIOutputDuplication
   ↓
ID3D11Texture2D
   ↓
rotation/pointer normalization
   ↓
crop / scale
   ↓
Detail swap chain
```

Desktop Duplication offers more control and metadata but pushes more responsibilities into Visual. `DuplicateOutput` is tied to the adapter owning the output, and a multi-output desktop uses separate duplication interfaces. Mode changes and certain desktop transitions can trigger `DXGI_ERROR_ACCESS_LOST`, requiring recreation.

**Likely complexity:** High.  
**Main advantage:** control and a strong performance comparator.  
**Main risk:** precisely the multi-adapter/USB-display world that Doxa may introduce.

**Approach C — Magnification API Detail control**

Set the windowed magnifier's source to a rectangle around the current POI and host the magnifier window on the Detail monitor. Microsoft exposes both source and transform operations through the Magnification API.

**Likely complexity:** Low for a proof of interaction.  
**Main question:** whether the API's constraints become awkward once Visual wants several independent sources, states and output monitors.

### Inspect + Return

For a **dedicated Detail monitor**, the clean implementation does not need to alter Windows or the source monitor at all.

Visual can model the interaction as:

```text
Normal view state
      ↓ trigger
push current ViewState
      ↓
temporary source/zoom around POI
      ↓ release / Esc
pop exact prior ViewState
```

“Return exactly” is therefore primarily a **state-management requirement**, not a graphics requirement. The saved descriptor should include source, source rectangle/POI policy, zoom, tracking policy and visual effects.

For **same-monitor Inspect + Return**, there are two credible routes:

1. let the Windows Magnification API temporarily transform/show a magnifier control, then restore it; or
2. place a custom captured enlargement above the original content.

The second option is more flexible but introduces a particularly important experimental risk: a monitor-capture pipeline may see its own overlay, producing recursive or stale imagery unless the capture/output relationship is deliberately handled. That specific behavior should be tested rather than assumed.

For the first user prototypes, **dedicated-detail inspection is materially cleaner** and more aligned with Doxa's differentiation.

### Independent per-monitor visual state

This does **not inherently require one fully separate magnification engine per monitor**.

A cleaner hypothesis is:

```text
CaptureSource
  ├─ View A → Output monitor A
  ├─ View B → Output monitor B
  └─ View C → Output monitor C
```

Each `View` owns:

- destination monitor;
- zoom;
- source/POI;
- tracking policy;
- visual-effect state;
- role;
- transient state.

A source monitor can therefore feed multiple outputs. WGC's design permits capture items/sessions and D3D surfaces to be consumed by application rendering code; whether a single captured frame can be fanned out with negligible extra cost is technically plausible but should be **measured, not assumed**.

Desktop Duplication supports the same high-level graph, but capture is fundamentally output/adapter-oriented, making the capture-source layer more complex on machines with multiple display adapters.

This source/view graph is one of the strongest reasons **not** to make “Monitor” the root architectural object.

### Mouse, caret and focus tracking

A plausible tracking service would expose normalized observations rather than commanding magnification directly:

```text
PointerProvider ───┐
CaretProvider ─────┼→ PointOfInterest service → tracking policy → View
FocusProvider ─────┘
ExplicitSelection ─┘
```

The important part is the policy layer. “Caret moved” does not necessarily mean “move Detail now.”

UI Automation provides the strongest semantic route for caret and focus, while WinEvent/GUI-thread APIs provide fallbacks. Microsoft security guidance, however, makes clear that assistive technologies crossing process integrity boundaries need to deal with UIAccess; ordinary medium-integrity processes cannot freely inspect higher-integrity UI, and even UIAccess does not grant access to the system secure desktop.

That implies two distinct production requirements:

**Application coverage:** does the target application expose usable UIA/caret/focus information?

**Security coverage:** is Visual permitted to observe it?

Those should not be mixed into one vague “tracking reliability” metric.

A robust implementation should also be prepared to **highlight without following**. If the focus signal is valid but its spatial location is uncertain, displaying a locator without moving the Detail viewport is safer than inventing a location.

### Monitor roles and workspace restoration

For role persistence, use Windows display configuration as the system topology source and maintain an application-level identity record. QueryDisplayConfig returns active display paths and DisplayConfig device-information calls expose target/source information under WDDM.

PowerToys provides concrete evidence for a composite record containing monitor instance ID, serial, monitor number, geometry, DPI and virtual desktop information.

Visual's likely role algorithm should therefore be tolerant rather than absolute:

**exact identity match → strong hardware metadata match → topology/geometry match → ask user/reassign**

That ordering is an architectural inference, not a documented Windows guarantee.

Workspace restoration should similarly distinguish:

- restoring **Visual state**, which Visual controls;
- restoring **ordinary window position**, which Visual can attempt;
- restoring **application internal state**, which Visual generally does not control.

PowerToys Workspaces demonstrates why this matters: some apps are single-instance, elevated applications complicate positioning, and restoration can visibly occur after launch rather than atomically at creation.

The factual API distinctions underlying this comparison are documented by Microsoft: WGC provides D3D capture frames; Desktop Duplication is output/adapter-based and requires explicit lifecycle/pointer/rotation handling; and the Magnification API supplies its own source/transform model.

**WGC + custom D3D11.** This is the most coherent first architecture hypothesis. It matches Visual's conceptual model unusually well: capture sources are separate from output views; D3D is already in the data path; per-monitor effects and independent zoom become render-state decisions; and Context + Detail need not alter the source desktop. The reason not to crown it prematurely is that the important unknowns — latency, USB displays, multiple adapters, capture exclusions and sustained fan-out — are empirical.

**Desktop Duplication + custom D3D11.** This buys more explicit control but also makes Visual responsible for several mechanisms WGC abstracts. The hard evidence against casually selecting it is Microsoft's own model: `DuplicateOutput` is created for a specific adapter output, pointer handling is partly explicit, rotations require client treatment, and duplication can be lost on system/display changes.

**Magnification API-centric.** This is the fastest way to determine whether users actually value Context + Detail or same-screen Inspect + Return. It is therefore commercially useful even if it ultimately loses the production architecture contest. The main danger is letting a cheap prototype API dictate the eventual product structure.

**Hybrid.** Use custom WGC/D3D views for multi-monitor features while retaining the Windows Magnification API for interactions where it is clearly superior, perhaps same-monitor temporary inspection. This has an appealing “best tool for each job” story, but also doubles lifecycle, test and support paths. It should be considered only if spikes show a concrete user-visible win. Complexity is not diversification; sometimes it is just twice the bugs.

## Prototype program and Doxa compatibility

The next step should be **technical spikes designed to kill architecture assumptions**, not a miniature Visual product.

### Capture-to-Detail latency and fan-out spike

**Question:** Can one conventional Windows source display feed a responsive magnified Detail display — and preferably two independent Detail views — using WGC without visible lag or instability?

**Minimal implementation:** On a normal dual/triple-monitor Windows 11 PC, capture one monitor through WGC. Render a cursor-centered crop at 2×/4× into a borderless D3D11 window on another display. Then add a second output view using the same source. No UIA, profiles, sharpening or polished UI.

**Measurements:** capture-frame cadence; capture-to-render delay; dropped/stale frames; GPU utilization; CPU utilization; behavior while scrolling a web page, dragging windows, playing ordinary video and moving the pointer rapidly; one-output versus two-output cost.

**Provisional success gate:** stable operation for at least 30 minutes without device/capture loss under ordinary use; 60 Hz source changes reproduced without persistent stutter on a conventional 60 Hz setup; p95 observed POI-to-Detail delay below roughly 50 ms as an engineering target. The 50 ms figure is **not established here as a low-vision usability threshold**; it is deliberately a stringent prototype gate to expose poor architecture early.

If WGC misses the gate, repeat the identical renderer with Desktop Duplication before optimizing anything else.

### Semantic Point-of-Interest spike

**Question:** Can Visual reliably locate mouse, caret and keyboard focus in the applications that matter, without viewport thrashing?

**Minimal implementation:** Build a diagnostic POI service, not a magnifier. Log pointer position, UIA focus events, `TextPattern2` caret range, fallback WinEvent/GUI caret information and normalized screen rectangle. Test Word, Excel, Outlook, Edge/Chromium, a representative Electron application such as Teams, File Explorer, Windows Settings and a simple Win32 editor.

**Measurements:** event-detection rate; spatial accuracy; latency from action to observation; duplicate events; false focus movement; applications/controls with no usable caret; behavior at ordinary versus elevated integrity.

**Provisional success gate:** focus location reliable in at least 95% of scripted priority interactions and caret location in at least 90% of scripted text-editing interactions before application-specific workarounds; zero uncontrolled feedback loops. These percentages are project engineering targets, not prevalence claims.

Failure here would materially change Visual's UX: it would argue for **visibility-first/manual movement** rather than broad automatic follow behavior.

### Mixed-DPI, rotation and topology spike

**Question:** Can one canonical coordinate layer eliminate observable drift across realistic monitor arrangements?

**Minimal implementation:** Build only a topology/coordinate visualizer. Place markers at pointer, focus and caret positions and reproduce their corresponding position in a captured Detail view. Exercise 100/125/150/200% scaling, negative monitor origins, portrait orientation, primary-monitor changes, hot-plug and sleep/resume.

**Measurement:** physical-pixel offset between expected and rendered POI; identity retained after topology events; time to recover after display change; whether conversion errors accumulate after repeated transitions.

**Provisional success gate:** no persistent coordinate drift; at most approximately 1–2 physical pixels of normalized targeting error in controlled test content; complete automatic recovery after supported topology changes without restarting Visual.

This spike should happen **before** sophisticated tracking is built. Otherwise every tracker bug will have a doppelgänger called “DPI”.

### Inspect + Return spike

**Question:** Which cheap mechanism best proves both dedicated-monitor and same-monitor inspection?

**Minimal implementation:** Prototype two versions: WGC/D3D temporary Detail on the second monitor and Windows Magnification API-based temporary same-monitor enlargement. Trigger with press-and-hold, center on mouse first, and restore a captured `ViewState` on release.

**Measurements:** trigger-to-visible time; exact state restoration; spatial disorientation; self-capture artifacts in the custom version; CPU/GPU overhead; failure after repeated rapid activation.

**Success gate:** repeated enter/return cycles leave the prior Visual state exactly unchanged; no cumulative spatial error or capture recursion; activation subjectively immediate enough to be used repeatedly in normal work.

### Doxa USB-display compatibility spike

This one deliberately occurs **after** the generic Windows pipeline works.

**Question:** Does the selected capture/render architecture remain valid on the actual Doxa display electronics/driver combination?

**Minimal implementation:** Run the unmodified WGC and Desktop Duplication test harnesses on the target Doxa dual- and triple-display revisions. Record Windows display topology/adapter ownership, capture each physical panel, render cross-panel Detail, unplug/replug, sleep/resume, rotate/change scaling, and exercise video plus Teams/Zoom.

**Measurements:** enumeration, adapter mapping, frame cadence, capture latency, CPU/GPU/USB load, cursor behavior, hot-plug recovery, sleep recovery, role identity stability and any black/unsupported capture paths.

**Failure gate:** any Doxa panel that cannot be captured by the selected production candidate; unacceptable frame pacing; inability to render source→destination across adapter boundaries; monitor identity changing unpredictably at ordinary reconnects; or substantial degradation when all three panels are active.

Silicon Motion publicly markets USB Display / Display Interface solutions, so USB graphics is a legitimate compatibility category rather than a hypothetical one. The public material located for this study does **not** document enough about the specific Doxa hardware/InstantView driver path to guarantee WGC or Desktop Duplication behavior.

That distinction is commercially important: **do not make the generic architecture Doxa-specific now, but do not call the architecture production-ready until it has survived Doxa hardware.**

Desktop Duplication deserves particular scrutiny on Doxa because Microsoft requires the D3D device passed to `DuplicateOutput` to belong to the adapter to which that output is attached. If a USB display is represented by Windows as a separate display adapter, Visual may need more than one capture device or a cross-adapter transfer strategy. That conditional conclusion follows from Microsoft's API contract; whether Doxa is actually exposed that way remains an unresolved physical-test question.

WGC might abstract this more conveniently, but Microsoft's documentation still provides an `IsSupported` check and does not establish that every third-party USB graphics path will meet Visual's latency and compatibility needs.

## Failure modes, open questions, and adversarial targets

### Material failure modes

**Secure desktop and privilege.** Desktop Duplication documents `E_ACCESSDENIED` for the secure desktop except under the appropriate system context. Microsoft's accessibility security guidance likewise makes clear that UIAccess assists with higher-integrity UI but does not turn an ordinary assistive application into a system-level secure-desktop observer. Visual should therefore have an explicit paused/unavailable behavior rather than attempting to promise magnification/tracking through UAC secure-desktop transitions.

**Elevated applications.** A non-UIAccess Visual process can encounter accessibility boundaries when attempting to observe elevated applications. UIAccess itself has signing, manifest and installation-location requirements. That is a deployment/product-signing concern as much as an API concern and deserves an early spike.

**Display/mode changes.** Desktop Duplication can report `DXGI_ERROR_ACCESS_LOST` around desktop switches and display-mode changes and must then be recreated. WGC frame pools also need recreation when size/device circumstances change. A production Visual cannot regard capture sessions as immortal.

**Rotation.** Desktop Duplication requires client-side rotation handling. This is not an exotic corner case for compact monitor systems, where portrait use may be quite plausible.

**HDR.** WGC documentation recommends using an HDR-capable floating-point format through the capture pipeline in HDR scenarios or explicitly tone-mapping, otherwise content may appear washed out. Unless research shows strong demand, full HDR correctness is a good candidate for “supported later”, not a reason to complicate the first architecture.

**Remote Desktop.** QueryDisplayConfig has documented restrictions in non-console/remote contexts, and remote sessions can change effective monitor/DPI topology. RDP should therefore be a declared support question, not accidentally inherited into the MVP.

**Office, Chromium/Electron and modern Windows UI.** UI Automation is the correct public semantic mechanism, but the application controls/providers determine what information is exposed. Even the recent HoverText project describes broader compatibility testing across browsers/editors/desktop applications as ongoing work, reinforcing that application coverage must be measured rather than assumed.

**Protected or noncapturable content.** The architecture should not assume every on-screen surface is always capturable. This research did not establish a sufficiently universal current Windows guarantee for DRM/protected content across every capture backend, so this remains a test case rather than a claim about exact black-frame behavior.

**Teams/Zoom and screen sharing.** Context + Detail itself can be built without solving screen-share policy. “Private Detail/Public Output” is a separate requirement: what a conferencing application captures depends on the user's selected share target and conferencing behavior. The core architecture should expose cleanly separable Visual output windows/monitors, but share-safe guarantees need a dedicated later study.

### Adversarial targets for DR-05

These are the claims that the next phase should try to **disprove**, not defend.

| Assumption to attack | What would falsify it |
|---|---|
| **“Windows Graphics Capture is responsive enough for continuous magnified Detail.”** | Measured delay/frame pacing makes cursor, typing or scrolling feel visibly detached. |
| **“One captured source can efficiently feed multiple independent Visual views.”** | Fan-out doubles capture cost, causes stalls, or forces undesirable copies. |
| **“A WGC-first architecture will work on Doxa USB displays without special handling.”** | A target panel is unsupported, black, slow, unstable or mapped to an incompatible graphics path. |
| **“Desktop Duplication is a practical fallback when WGC fails.”** | Adapter ownership/cross-device copying on real Doxa hardware makes it more fragile than WGC. |
| **“D3D11 provides all rendering control Visual realistically needs.”** | Profiling reveals a requirement that cannot be met without a materially different graphics architecture. |
| **“Physical virtual-desktop pixels can be the canonical coordinate system.”** | UIA/Win32/capture transforms cannot be normalized reliably across mixed DPI, rotation and negative origins. |
| **“UI Automation plus Win32 fallbacks gives sufficiently reliable caret tracking.”** | Word/Excel/browser/Electron test tasks frequently have no usable or timely caret geometry. |
| **“UI Automation focus events are stable enough to drive automatic viewport movement.”** | Duplicate/transient focus events produce perceptible jumping even after sensible filtering. |
| **“UIAccess provides enough elevated-application coverage for the commercial target.”** | Important professional software remains inaccessible or deployment requirements are unacceptable. |
| **“Monitor roles can survive reconnects of two or three visually identical portable panels.”** | Windows/driver identity changes or identical serial/instance data make roles ambiguous frequently enough to annoy users. |
| **“Same-monitor Inspect can use the same custom capture pipeline as dedicated Detail.”** | Self-capture recursion, latency or visual discontinuity makes a separate mechanism necessary. |
| **“Capture/render sessions can recover transparently from docking, sleep and hot-plug.”** | Users regularly see stuck/black views or need to restart Visual. |
| **“Best-effort workspace restoration is good enough to support meaningful Monitor Roles.”** | Major applications launch or reposition unpredictably enough that role restoration becomes a support burden. |
| **“A 60 Hz-oriented pipeline is sufficient for the target compact-display experience.”** | High-refresh displays or rapid pointer/scroll tasks reveal unacceptable perceived lag despite nominal frame rate. |
| **“Stable Context + Detail actually reduces navigation effort enough to justify this technical machinery.”** | User testing shows users watch only Detail, become confused by correspondence between views, or perform better with simpler temporary zoom. |

That last target is deliberately not technical. It should still be attacked. A flawless implementation of an invalid product assumption is merely a very well engineered mistake.

### Decision implication

The simplest credible route to Visual is now reasonably well bounded:

**For the first serious technical prototype**

```text
Windows 11 / Per-Monitor-V2 process
          │
          ├── Display topology + persisted roles
          │
Source ── WGC ── D3D11 frame
                    │
                crop around POI
                    │
              D3D11 scale/effect
                    │
               Detail HWND
                    │
             destination monitor

Pointer ────────────┐
UIA caret ──────────┼── Point-of-Interest policy
UIA/WinEvent focus ─┤
Explicit selection ─┘
```

This is supported by public Windows primitives rather than speculative proprietary technology: WGC supplies captured D3D frames; D3D11 supplies the rendering layer; UI Automation exposes semantic caret and focus information; WinEvent/GUI APIs provide fallbacks; display-configuration APIs expose topology; and PowerToys demonstrates practical monitor-identity and workspace patterns on contemporary Windows.

**Desktop Duplication should be treated as the principal challenger**, not automatically as the foundation. It offers strong control and a well-established D3D path, but its per-output/adapter semantics, explicit cursor/rotation handling and access-loss lifecycle make it more engineering-intensive precisely in the multi-adapter scenarios Visual may encounter later.

**The Windows Magnification API should be treated as a prototype accelerator**, particularly for same-monitor Inspect + Return, rather than assumed to be either obsolete or sufficient for the whole product. Microsoft's API still exposes the basic transformations Visual needs, but the custom multi-view architecture is more naturally represented by capture sources and independent rendered views.

The provisional architecture principle with the strongest evidence is therefore not “use WGC” or “use D3D11”. It is more fundamental:

> **Make capture sources, Points of Interest, visual transformations and destination monitors independent objects.**

That model directly supports Stable Context + Detail, dedicated Inspect + Return, independent monitor state, fixed references, per-monitor visual effects and role-based screens without requiring each new feature to become another global magnifier mode.

The most consequential work before architecture selection is correspondingly small: **prove the capture/render latency, prove the POI signals, prove the coordinate model, and then prove the exact same pipeline on Doxa USB hardware.** Until those four propositions survive deliberate attempts to break them, choosing a final architecture would be premature closure rather than engineering certainty.
